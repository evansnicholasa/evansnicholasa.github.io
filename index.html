Does an LLM beat a simple baseline at triaging test failures?

Measured, not assumed · TypeScript, Playwright, Python

A test goes red overnight. Someone has to decide whether the product is broken, the test is broken, the environment is broken, or it is simply flaky. That call is most of what triage is, and getting it wrong in the direction of blaming the product is how a team stops trusting its own suite.

I wanted to know whether a language model does that better than something simple. So I built the measuring instrument first: a deliberately defective application and API with twenty-two cataloged defects and four injectable flakes, each carrying the classification a correct triage system should assign. Every failure it produces has a known right answer. That repository contains no AI at all, deliberately — an instrument that shares components with the thing it measures is not worth much.

The model lost. Deterministic clustering — group failures by their error evidence, label each group by what it has historically been — scores 73.2% macro F1 at zero cost and with no dependencies. Adding claude-opus-5 on the ambiguous cases dropped that to 61.3% and cost $0.31 a run.

The whole gap is one behavior. The model finds exactly the same real broken tests the clustering finds — identical recall — then labels twenty more failures "broken test" that were not. Five of those were genuine product bugs.

It was also weakest on the deliberately ambiguous cases, which is precisely where the argument for reaching for a model is strongest. Two cross-run frequency hypotheses that sounded obviously right contributed nothing, measured three separate ways.

The labeled corpus is published as a checksummed release and cited by tag, so the numbers can be reproduced rather than taken on faith — the deterministic baseline runs from a clean checkout with one command and no credentials. An earlier version of this result was measured against a corpus that was later regenerated, which quietly made the published figure unverifiable. Fixing that honestly is documented in the repository alongside the superseded numbers.

Job Tracker — full-stack, self-hosted

A working application, not a demo · FastAPI, MariaDB, React

Tracks job applications end to end: company, role, source, status, salary range, dates, notes, next action and contacts. A FastAPI service in Python with SQLAlchemy models and Alembic migrations, running against MariaDB over the MySQL wire protocol, with a React single-page front end built in Vite.

Two repositories deployed independently, with requirements and architecture in a third that both consume as a git submodule — one source of truth rather than copies that drift. Two Chrome extensions sit alongside them: one scrapes a posting and files it, the other marks an existing application closed in a single click. The whole thing runs on a self-hosted Debian machine, with work tracked in Jira.

jira-cli — replacing a metered integration with 330 lines

A small tool that removed a subscription · Python, zero dependencies

I was driving the Jira board for that project through Atlassian's hosted Rovo MCP server. It worked, but it meters against Rovo credits and is not offered on the Free plan — so keeping one integration alive meant paying for a tier I had no other use for. The REST API underneath it is available on every plan, unmetered.

So I wrote about 330 lines of Python that talks to it directly: a single file, no dependencies, any Python 3.9 or later. Two things turned out better rather than merely cheaper. It runs anywhere there is a shell — a terminal, an editor, a CI job, more than one AI coding agent — where an MCP server only works where it has been configured. And it can be read, tested and changed, which a hosted service cannot.

Having no dependencies is a working decision rather than an aesthetic one: a tool you reach for every few weeks is one whose dependencies rot between uses, and the first run after six months should not begin with a resolver error. transition takes a status name rather than Jira's internal transition id and makes the lookup round trip itself — and when the status is not reachable from where the issue currently sits, the error lists the ones that are, because "no" on its own is a useless answer.
